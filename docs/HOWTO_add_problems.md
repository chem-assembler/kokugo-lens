# 問題を足す手順（並列で量産するときの型）

2026-08-12 に **78問 → 140問**を1日で積んだときのやり方をそのまま手順にしたもの。
道具は `kanbun/tools/` にある。**この手順から外れると、過去に実際に起きた事故を踏み直す。**

## いま何が残っているか（まず数える）

```bash
node kanbun/tools/uncollected.js catalog
```

`docs/material-catalog.md`（先秦〜唐宋）の未収録行が出る。2026-08-12 時点で **498行中51行が収録済み**。
明清（`material-minqing.md`）は消化しきった。

**この数字を README の記述より信用すること。** 過去に README の「残っている穴」が
事実と違っていて、実際に無駄足を踏んだ。

## 二つの道がある

| | 中で作る（レーン） | 外に投げる（Gemini） |
|---|---|---|
| 誰が訓読を決めるか | 自分（サブエージェント） | Gemini |
| 返り点を組むのは | 自分 | **自分**（外には任せない） |
| 向くもの | 少量・判断が要るもの | **まとまった量**・定訓が安定しているもの |
| 手順 | 下の 1〜6 | 下の **0** → 3〜6 |

**返り点はどちらの道でも自分で組む。** 書き下しが決まれば返り点は一意に決まるし、
符号づけはこのアプリのエンジンの規則そのものなので、外から当てにいくと外れるだけ。

### 0. Gemini に投げる（外に出せるものは出す）

```bash
node kanbun/tools/gemini-pack.js S 36     # docs/gemini-pack-kanbun-s-1..4.md ができる
```

台帳の**未収録行だけ**を切り出して、そのまま貼れる依頼本文にする。
**白文を人が写さない**のが要点（写し間違いは実際に3回起きている）。
字体の正規化も `kyujitai.js` を通すので台帳と1バイトもずれない。

Gemini が返す JSON（読む順に並べた字・書き下し・置き字・再読・句法・意味・自信）を
そのまま次に流す。

```bash
node kanbun/tools/gemini-intake.js <Geminiの出力.json> S <出力先lane.json>
```

ここで **order を作り、返り点まで機械で組み、組んだ訓点をエンジンに読ませて突き合わせる**。
Gemini の申告と機械の導出が食い違えば落ちる。`confidence` が「高」でない行は既定で保留に回る。
通ったものは `id` と `source.work` だけ人が埋めて（`chapter` は台帳から入っている）、
`_catalog` `_section` `_confidence` を消してから手順3へ。

**通ったからといって教えとして正しいとはかぎらない。** 書き下しが定訓か、
句法タグが型の書き下しと食い違わないかは、収録前に必ず人が読むこと。

## 手順

### 1. レーンに割る

作品や句法のカテゴリで3〜4に分け、1レーン5問前後にする。
**狙いは数ではなく「実例が薄い型を厚くすること」**のほうが効く。薄い型はこれで出る。

```bash
node -e "const d=require('./kanbun/kuho.json');d.types.filter(t=>t.examples.length<=1).forEach(t=>console.log(t.examples.length+'件 '+t.id+' '+t.name))"
```

### 2. レーンにリポジトリを触らせない

各レーンは**スクラッチパッドの自分のファイル**（`lane-A.json` など）にだけ書く。
並行して repo を書くと衝突する。**ここは譲らないこと。**

### 3. 提出前に、レーン自身に検査を通させる

```bash
node kanbun/tools/lane-verify.js <レーンのJSON>
```

訓点から導いた読み順が申告と一致するか、トークンから生成した書き下しが申告と一致するかを
**実際のエンジンで**確かめる。**「不備なし」が出るまで直させる。**
二重帳簿の検査をレーンの内側に持たせるのが要点で、これで合流時に落ちるものが無くなる。

### 4. 合流する

```bash
node kanbun/tools/lane-merge.js <レーンのディレクトリ>            # 検査だけ
node kanbun/tools/lane-merge.js <レーンのディレクトリ> --write   # 収録
```

レーン単独では見えない事故（id の衝突・同じ白文の二重収録）はここで見る。
**済んだレーンのファイルは別のディレクトリへ退避すること。** 残っていると
「すでに収録済み」で止まる（これは設計どおりの動作）。

### 5. 型と結び直す ← **忘れやすい**

問題を足すと、句法クイズの解説から訓点モードへ渡すカードが取りこぼされる。
68問足したあと、結び付いた問題は 65/133 まで落ちていた。

```bash
node kanbun/tools/link-verify.js <案のJSON>            # 検査だけ
node kanbun/tools/link-verify.js <案のJSON> --write   # 収録
```

案の形は `{ "型id": ["問題id", ...] }`。

### 6. 版を上げて全部通す

```bash
sed -i 's/v=NN/v=MM/g; s/>vNN</>vMM</g' kanbun/game.js kanbun/guide.html kanbun/guide.js kanbun/index.html kanbun/kudashi.html kanbun/kudashi.js kanbun/kuho.html kanbun/kuho.js kanbun/test.html
node kanbun/tests.js && node kanbun/kuho-check.js && node kanbun/yomi-check.js && node kanbun/guide-check.js && node qa/check.js
```

そのうえで**ブラウザ実機**で新規問題を L1（読む順にタップ）で最後まで解けることを通しで確かめる。
`python -m http.server 8138` → `http://localhost:8138/kanbun/`。

## 踏んではいけない穴（すべて実際に起きた）

**台帳の返り点欄はよく間違っている。** 明清の台帳で **11件**の誤りを訂正した。型は4つ。
返り点が要らない句を「必要」と書く／返り先が2字なのに「レ点」と書く（レ点では届かない）／
副詞を返りの連鎖に入れる／レ点にすると句が壊れる箇所をレ点と書く。
**指示は参考にとどめ、自分で組んで検証を通すのが最終判断。**

**文字コードの取り違えが3回起きた**（羞→翞、辨→辯、衰→衅）。
Unicode のエスケープで書かず、**文字そのものを書くこと**。書いたら白文を台帳と機械照合する。

**機械検査を通ることと、教えとして正しいことは別。**
「不已為若笑耶」は標識「為」があるので助字の受身の検査を通ってしまうが、
型の書き下し「Aセらル」とこの問題の「〜と為る」が食い違い、穴埋めで誤答を誘う。
**機械が出した候補をそのまま採らないこと。**

**旧字体の対応表に抜けがあると「収録済み」を「未収録」と誤って数える。**
抜けは機械で洗える（収録済みの白文と台帳の行を突き合わせ、同じ長さで1〜3字だけ違う組を報告）。
この方法で15字を見つけて台帳 §8.1 に補った。

**`yomi`（読み仮名）は二重帳簿の盲点。** `toKakikudashi` は漢字トークンの `c + okuri` しか
使わないので、読みを壊してもテストが緑のまま通る。`node kanbun/yomi-check.js` を必ず走らせる。
ただしこの検査も**型に当てはまる誤りしか捕まえない**（限界はファイル冒頭に明記してある）。

## 収録の判断（迷ったときの原則）

- **確実な1件のほうが、あやしい5件より価値がある。** 迷ったら入れずに報告する
- **切り出しが句形を壊すなら入れない。** 実例: 抑揚の「軽い側」の否定を落として
  意味と書き下しが食い違った行は、収録を見送って台帳に理由を書いた
- **定訓を曲げてまで型に当てはめない。** 「勧君更尽一杯酒」を使役にすれば形は作れるが作らない
- 隣接の返りは**レ点**（実測でレ点76件・一二点10件）。ただし返り先が2字以上ならレ点では届かない
- 時・場所の「於」は**置き字**。返り点の二段目は**「下」**（上・中で止めない）
- 文末の「也」は**「なり」と読む**（既存データの多数派）
- `acceptable`（別解）は**送り仮名の違いだけ**。漢字が変わる別解はカードで到達できず回帰テストが弾く
