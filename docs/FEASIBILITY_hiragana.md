# 全部平仮名の書き下し（阪大型）は機械で採点できるか — 見極めメモ（2026-08-12）

これは設計書ではない。**「作れるか」だけを判定する**ためのメモ。
結論を先に書き、根拠として実際に走らせたプロトタイプの結果を置く。手本は `docs/FEASIBILITY_kobun.md`。

計測はすべて作業ツリーの `kanbun/texts.json` を `node` で走らせたもの。
**着手時 133問 → 判定中に 140問に増えた**（別レーンが並行して問題を足している）。
以下の絶対数は 140問時点。**比率と構造は 133問時点と変わらなかった**（両方で測って確認済み）。

---

## 結論

**条件つきで作れる。条件は2つで、どちらも有限の作業。**

| | 問い | 答え |
|---|---|---|
| 1 | 漢字かな交じりから全部平仮名の正解を機械で作れるか | **作れる。140/140 で生成できた。ただし内容が正しいのは 133/140** ＝ **7問はデータを直す必要がある**（1問あたり1トークン。修正案も確認済み） |
| 2 | 歴史的仮名遣いと現代仮名遣いの両方を正解にできるか | **できる。ただし現状の `normalizeKana`/`kanaEquals` では全く足りない**。人が書いた現代仮名遣い40問のうち**現状は 8問しか通らない**。変換を4種足すと **39/40**（残り1件は上記データ誤りが原因で、直すと 40/40） |

**条件A（データ）**: 7問の `yomi` を直す。機械で候補を6+3件に絞れる（下の帳簿2c）。
**条件B（コード）**: `normalizeKana` に**4種の変換**を足す。閉じた知識で、データとの同期が要らない。

**やらないと決めてよいこと**: 撥音「む→ん」の変換は**不要**。corpus の「む」14種はすべて動詞の語尾で、
撥音はすでに「ん」で書かれている（`okuri` に「ん」を含むトークンが37件）。入れると採点が緩むだけ。

## 根拠1: 全平仮名の正解は機械で作れる（帳簿1・2）

`tokens[i].yomi + tokens[i].okuri` を `order` の順に連結し、カタカナをひらがなに落とすだけ。

```
== 帳簿1: 全平仮名の書き下しを生成できるか ==
  140 / 140 問で生成できた
```

読みの欠けたトークンは**ゼロ**（漢字トークンで `yomi` が空 = 0件、`yomi` に仮名以外が混じる = 0件、
再読文字1枚目の `yomi` が空 = 0件）。データ側の準備は整っている。

**新しいフィールドは要らない。** 生成に必要なものは全部 `yomi`/`okuri`/`kana`/`reread`/`role` にある。

### 帳簿2（逆写像）＝ 生成が既存の正解と食い違わないことの機械証明

生成しながら「この文字は `yomi` 由来／`okuri` 由来」を記録し、**`yomi` 由来の区間を漢字に戻す**と
`problem.kakikudashi` に戻るはず、という照合をかけた。

```
== 帳簿2: 逆写像 ==
  140 / 140 問で一致（既存 toKakikudashi との突合も 140 / 140）
```

わざと壊すと弾ける。

```
== 対照: わざと壊したデータを帳簿1・2 が弾くか ==
  ○ 弾けた  「思」の yomi を空にした            → 帳簿1 が読みを取れないと言う
  ○ 弾けた  「思」の okuri を ハ→ヒ に壊した     → 帳簿2 復元「思ひざれば」≠「思はざれば」
  × 素通り  「学」の yomi を まな→まなん に壊した ← ここが穴
  ○ 弾けた  読み順を壊した                      → 帳簿2 復元「学びてざれば思は…」
  × 素通り  （対照）壊していない
```

**3行目が本メモでいちばん重要な発見**。理由は次節。

## 根拠2: `yomi` は「表示専用の第2の真実」である（最大の弱点）

`toKakikudashi` は漢字トークンについて **`t.c + okuri`** しか使わない（kanbun.js:120）。
**`yomi` は `kana:true` のトークンでしか書き下しに現れない**。つまり:

- 既存の二重帳簿（`validateProblem`）は **漢字トークンの `yomi` を一度も検査していない**
- `yomi` はルビとして画面に出るだけの表示データで、**機械的には野放し**

全平仮名モードは、この野放しのフィールドを**正解キーに昇格させる**。

```
全平仮名文の総字数 2975字
  漢字の読み yomi（機械未検証）  1692字 = 56.9%
  送り仮名 okuri（検証済）         961字
  仮名トークン（検証済）           322字
```

**正解キーの 57% が、これまで誰も機械で検査していなかった文字列**。これが本件の本質的な難所であり、
「作れる／作れない」ではなく「条件つき」と書いた理由。

### 実際に7問が壊れていた（帳簿2c）

2種類の網で探した。どちらも既存の `validateProblem` をすり抜ける誤りを捕まえた。

**網1: 重複ルビ**（`yomi` の末尾と `okuri` の先頭が重なる ＝ ルビが送り仮名を食っている）

```
  重複ルビ候補: 6 件
    rongo-tomo             来 きた+たる→きたたる   ← ✗ 正しくは きたる
    hango-ani              遽 にはか+かに→にはかかに ← ✗ 正しくは にはかに
    katei-moshi            此 これ+れを→これれを    ← ✗ 正しくは これを
    mq-zaien-senyo         皮 かは+は→かはは       ← ○ 皮＋は（係助詞）で正しい
    mq-ryosai-imada        聞 き+きて→ききて       ← ○ 聞きて で正しい
    mq-gozasso-nannnotsune 之 これ+れ→これれ       ← ✗ 正しくは これ
```

6件中4件が本物の誤り。**機械が6件に絞り、人が2件を落とす**という分業で済む。

**網2: 送り仮名なしの「亦」**（`亦` 単独は「また」と読むのに `yomi` が「ま」）

```
  送り仮名なしの 亦/又/復: 3 件
    hango-mata / mq-gozasso-madoi / mq-gozasso-mube   すべて 亦=ま
```

corpus 内の他の「亦」は `yomi=ま okuri=タ`（＝また）なので、送り仮名なしの3件だけ「ま」で切れている。
ルビの書き写し事故と見られる。**L1〜L3 の画面ではいま「亦(ま)」と表示されているはず**（未確認・要目視）。

### 7問とも1トークンの修正で直り、既存テストは前後とも通る

```
== 対照: 疑わしい7問を1トークンだけ直すとどうなるか ==
  rongo-tomo              修正前 × ともありゑんぱうよりきたたる
                          修正後 ○ ともありゑんぱうよりきたる

  hango-ani               遽 にはか+カニ → には+カニ        修正後 ○

  mq-gozasso-nannnotsune  之 これ+レ    → こ+レ            修正後 ○
  hango-mata              亦 ま         → また             修正後 ○
  mq-gozasso-madoi        亦 ま         → また             修正後 ○
```

**「前 ○ / 後 ○」がこの表の要点**。既存の二重帳簿は壊れたデータも直したデータも同じく通す ＝ 盲。

## 根拠3: 仮名遣いの吸収は「現状では全く足りない」（帳簿3）

### 現状の実装が実際にやっていること（コードを読んで確認）

| 関数 | 行 | 中身 |
|---|---|---|
| `normalizeKana` | kanbun.js:135-141 | カタカナ→ひらがな／記号除去／`ゐゑを`→`いえお`／`ぢづ`→`じず` |
| `transposeHagyo` | kanbun.js:144 | 非語頭のハ行→`わいうえお`（ハ行転呼の近似） |
| `kanaEquals` | kanbun.js:145-148 | 上を**両辺にかけて**比較 |

**「両辺にかける」という作法が効いている**のが重要。片側だけを現代仮名遣いに寄せるのではなく、
両方を同じ標準形に落とすので、規則が言語学的に厳密でなくても等価性は保たれる。
拡張もこの作法に従えばよい（例: 「たいはう」→ハ行転呼→「たいわう」→開合→「たいおう」、
学習者の「たいほう」→ハ行転呼→「たいおう」。途中の形は言語学的に無意味だが、両辺は一致する）。

### 人が書いた現代仮名遣い40問との照合（★ここが判定の中心）

## 足りない変換の一覧（実データから洗い出したもの）

**★が必要な追加。**「該当問題数」は 140問中。

| # | 変換 | 例 | 該当問題数 | 判定 |
|---|---|---|---|---|
| ★1 | **合拗音** `くわ`→`か` / `ぐわ`→`が` | くわういん→こういん（光陰）／ぐわつ→がつ（月） | **11** | 必要 |
| ★2 | **開合** あ段+`う`→お段+`う` | かうべ→こうべ／たいはう→たいほう／さうえふ→そうよう | **26** | 必要 |

| — | ハ行転呼（既存） | おもふ→おもう | 103 | 実装済み |
| — | `ゐゑを`→`いえお`（既存） | をとこ→おとこ | 74 | 実装済み |
| — | `ぢづ`→`じず`（既存） | なんぢ→なんじ | 16 | 実装済み |

**★1〜★5 のいずれかが必要な問題は 79 / 140（56%）。** 半数以上なので「例外的な少数を acceptable で拾う」
では済まない ＝ **正規化のコードに入れるべき性質のもの**。

**★5 は学習者の表記ゆれ対策であると同時に、データ自身の揺れの吸収でもある。**
corpus は同じ字を両様に書いている:

```
  者: しや(gaishi-seija) / しゃ(mq-bunkan-bensezu) / じゃ(mq-chihoku-senja)
  朝: てふ(shiki-kanshi) / てう(mq-ryosai-karu)      ← 字音は「てう」。てふ は蝶。要確認
  以: もつて（大書きつ・8問） ⇔ 一: いっ（小書きっ・11問）
```

（`朝` の `てふ`/`てう` は★3で両方「ちょう」に落ちるので**採点には影響しない**。データの見た目の問題。）

**6（む→ん）を不要と判定した根拠**: corpus の「む」を含むトークン14種はすべて動詞語尾
（`使:しむ` `寧:むしろ` `拒:こばむ` `恨:うらむ` `始:はじむ` `惜:をしむ` `治:をさむる` …）で、
**助動詞「む」は1件も無い**。撥音はすでに「ん」で書かれている（`okuri` に「ん」を含むトークン37件）。
入れると採点が緩むだけで得るものがない（下の 0.660%→0.773%）。

## 緩すぎないかの検査（帳簿4）

**変換を足すほど採点は緩くなる。** どれだけ緩むかを2つの角度で測った。

**(a) 別問題どうしが同一視されないか（総当たり）**

```
  L0 現状 kanaEquals        衝突 0 件
  L1 +小書き統一             衝突 0 件
  L2 +字音仮名遣い           衝突 0 件   ← 推奨案でも衝突ゼロ
  L3 +撥音 む→ん            衝突 0 件
```

**(b) 1文字だけ変えた入力が「正解」になってしまう率**（140問 × 全位置 × 45仮名 = 128,551通り）

```
  L0 現状 kanaEquals        632 / 128551  (0.492%)
  L1 +小書き統一             686 / 128551  (0.534%)
  L2 +字音仮名遣い           848 / 128551  (0.660%)   ← +216件
  L3 +撥音 む→ん            994 / 128551  (0.773%)
```

増えた216件の内訳を数えたところ、**すべて規則が意図的に同値化した組**だった。

```
  ゃ→や×21  っ→つ×12  ょ→よ×11  ゃ→え×11  ゃ→へ×11  ゃ→よ×11
  や→え×10  や→へ×10  や→よ×10  ゅ→ゆ×10  を→あ×7  …（全44種）
```

たとえば「や→え」は `やう→よう` と `えう→よう` が同じ現代仮名遣いに落ちるためで、
**現代仮名遣いを受理する以上は避けられない同値化**（歴史的仮名遣いの情報落ちそのもの）。
語として別物になる衝突は (a) のとおりゼロ。

## 弱点・成立を疑うべき点（正直に）

**1. 正解キーの 57% が機械未検証の `yomi` である。**（最大の弱点）
帳簿2の逆写像は **`okuri` と読み順しか守れない**。`yomi` を「まな→まなん」と壊しても素通りする
（上の対照で実測）。今回7問見つけたが、**見つけ切ったという保証はどこにもない**。
2つの網（重複ルビ／亦）は**思いついたパターンしか捕まえない**。
→ 現実的な受け皿は「**一度人が140本の平仮名文を通読し、以後はスナップショットで固定する**」。
これは漢文アプリがこれまで避けてきた「人が第2の真実を保守する」形にいちばん近い。
**この一度の通読を許容できるかが、着手の可否そのもの。**

**2. 「読み仮名を問う」という学習価値は、実は薄いかもしれない。**
`DESIGN_kudashi_input.md` 論点3-3 が自分で書いている ——「読み仮名は L1〜L3 でルビとして
**常時表示されている既知情報**で、当てさせても学習価値が薄い」。全部平仮名は、その既知情報を
全部書かせる形式である。**入試で問われるから作る**という以上の理由が要る。
逆に言えば、**新しく学習価値が生まれるのはまさに字音仮名遣いの部分**（てふ／ちょう）で、
そこは★1〜★5 で**全部正解にしてしまう**。**採点を成立させる仕掛けが、学習価値を消す**という
ねじれがある。これが本件でいちばん怪しい点。
→ 逃げ道: 誤答面ではなく**クリア面**で「登録の形は『てふ』（歴史的仮名遣い）です」と併記する
（`gradeReadings` の `variant.via` の仕組みがすでにある）。採点は緩く、提示は厳しく。

**3. 入力量が K3 より一段重い。**
1問の平仮名文は平均21字（2975字 ÷ 140問）、最長は `mq-riennso-subekaraku` の60字超。
K3 は送り仮名だけ（1問5枚上限）だったが、全部平仮名は**文全体を1つの入力欄に打たせる**。
UI はむしろ単純になる（カード単位の入力もボトムシートも不要。テキストエリア1つ＋
`matchesKakikudashi` 相当を平仮名版に差し替えるだけ）が、**離脱要因としては K3 より重い**。
設計書 §5 の「作業になり離脱要因になる」は全部平仮名にこそ当てはまる。

**4. 「並べ替え」との関係を決めていない。**
K1〜K3 はカードを並べる操作が土台にある。全部平仮名は**並べ替えが不要**（打った文がそのまま答え）。
**同じ画面の段として足すのか、別モードにするのか**が未決。段として足すと、
`progress.js` の `MODES` を触らない方針（論点3）との整合を再確認する必要がある。

**5. `acceptable[]` は平仮名版には流用できない。**
現在の5件は漢字かな交じりで登録されており、`acceptableShapeOk`（kanbun.js:400-417）は
**読む順に漢字を拾った正規表現**で照合する。平仮名の別解はこの検査に必ず落ちる。
平仮名版の別解を持つなら**別フィールド**か、**登録済みの別解を平仮名化して受理する導出**が要る
（後者なら第2の真実を増やさずに済む。未検証）。

**6. 未確認**: 阪大の実際の設問文（「すべて平仮名で」の指示が現代仮名遣い指定なのか歴史的仮名遣い
可なのか）を `exam-kanbun-sources.md` で確かめていない。**採点の緩さをどこまで許すかの根拠**が
そこにあるはずで、本メモの★1〜★5 は「両方受理」という前提で組んである。

## 次の一手（着手するとき）

**古文と同じく「検査を先に、データを後に」の順序で。**

1. **`kanbun.js` に `toHiragana(tokens, order)` と、逆写像の検査を書く**（コード20行程度）。
   `tests.js` に総当たりで「全問題で逆写像が `kakikudashi` に戻る」を1本。
   ここまでは**採点にも UI にも触らない**ので、いつ入れても安全。
2. **帳簿2c の2つの網を `validateProblem` に足す**（重複ルビ／送り仮名なしの `亦`）。
   6+3件が出るので、7件を直し2件を除外リストに入れる。**`yomi` が初めて機械の網に入る**。
3. **140本の平仮名文を人が一度通読する**（弱点1）。合格したものを
   `tests.js` にスナップショットで固定 ＝ 以後の回帰は機械が見る。
   **この工程を飛ばすなら着手しないほうがよい。**
4. **`normalizeKana` に★1〜★5 を足す**。順序は
   `合拗音 → え段+う → い段+う → あ段+う`（カスケードしないことを確認済み）。
   小書き統一は `transposeHagyo` の後、字音変換の前。
   `tests.js` に (a) 代表語21対、(b) 140問の総当たり衝突ゼロ、(c) 1文字改変率の上限、
   (d) **既存の `kanaEquals` が真を返す組はすべて拡張版でも真**（後退がないこと）を入れる。

リポジトリのファイルは読むだけで書き換えない。中核は以下。

```js
// 生成（帳簿1）＋ 逆写像（帳簿2）: yomi 由来の区間を c に戻すと kakikudashi に戻るはず
function build(problem) {
  const seen = new Map(); let hira = ''; const pieces = [], missing = [];
  for (const i of problem.order) {
    const t = problem.tokens[i], n = (seen.get(i) || 0) + 1; seen.set(i, n);
    let y, o, isKana;
    if (t.reread) { const r = n === 2 ? t.reread.second : t.reread.first;
      y = KH(r.yomi||''); o = KH(r.okuri||''); isKana = !!r.kana; }
    else { y = KH(t.yomi||''); o = KH(t.okuri||''); isKana = !!t.kana; }
    if (!isKana && !y) missing.push({ i, nth: n, c: t.c });
    if (isKana) pieces.push({ kind:'o', text: y + o, c: '' });
    else { pieces.push({ kind:'y', text: y, c: t.c }); pieces.push({ kind:'o', text: o, c: '' }); }
    hira += y + o;
  }
  return { hira, restored: pieces.map(p => p.kind === 'y' ? p.c : p.text).join(''), missing };
}

// 拡張正規化（★1〜★5）。既存と同じく「両辺にかけて比較する」作法を守る
const unify = s => s.replace(/[ゃゅょっゎ]/g, c => ({ゃ:'や',ゅ:'ゆ',ょ:'よ',っ:'つ',ゎ:'わ'})[c]);  // ★5
function onbin(s) {
  let t = s.replace(/くわ/g,'か').replace(/ぐわ/g,'が');                                    // ★1
  t = t.replace(/([けげせぜてでねへべぺめれえ])う/g, (m,a) => E2YO[a] + 'う');               // ★3 てう→ちよう
  t = t.replace(/([きぎしじちにひびぴみりい])う/g,   (m,a) => I2YU[a] + 'う');               // ★4 きう→きゆう
  t = t.replace(/([かがさざただなはばぱまやらわあ])う/g, (m,a) => A2O[a] + 'う');            // ★2 かう→こう
  return t;
}
const normExt = s => onbin(unify(transposeHagyo(K.normalizeKana(s))));
const kanaEqualsExt = (a, b) => normExt(a) === normExt(b);
```

`E2YO` は `け→きよ せ→しよ て→ちよ ね→によ へ→ひよ め→みよ れ→りよ え→よ`（＋濁音）、
`I2YU` は `き→きゆ し→しゆ ち→ちゆ … い→ゆ`、`A2O` は `か→こ さ→そ た→と な→の は→ほ
ま→も や→よ ら→ろ わ→お あ→お`（＋濁音・半濁音）。小書きを先に大書きへ統一しているので、
規則はすべて大書きの空間で書ける（`しやう` と `しょう` を1本の規則で扱える）。
