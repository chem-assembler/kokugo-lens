# 書き下し練習に読み仮名・送り仮名の入力を足す（設計）

対象: `kanbun/kudashi.js` + `kanbun/kudashi.html`（書き下し練習）。
上位の設計書は `../DESIGN_kanbun.md`。とくに §4.2（書き下し生成）・§4.3（採点と仮名の正規化）・
§6.3（書き下し練習のカード D&D）・§5（足場を外す段階）を具体化する。

**この文書は設計だけで、実装は含まない。**

計測値はすべて作業ツリーの `kanbun/texts.json`（v10 作業中・**58問**）を `node` で数えたもの。
別セッションが同じファイルを触っているため、絶対数は数問ずれうる。**比率と構造は変わらない**。

---

## 1. 目的と、いま何ができていないか

### 1.1 いまのコードが実際にやっていること

`kudashi.js` は白文カードを「読む順」トレイに並べさせ、**並びだけ**を採点する。
読み仮名・送り仮名の入力は**どこにも無い**。事実として:

- **読み仮名は「見せる」だけ**。`refresh()`（kudashi.js:139-148）は `showYomi` が真のとき
  `t.yomi`（再読文字なら `t.reread.first.yomi` / `.second.yomi`）を `.yomi` スパンに流し込む。
  **`okuri` は一度も画面に出ない**。トグルは `btn-yomi`（kudashi.js:265-269）。
- **書き下しはデータから作っている**。クリア時の表示は
  `K.toKakikudashi(problem.tokens, expectedOrder())`（kudashi.js:210-211）＝
  **正解の `order`＋データの `yomi`/`okuri`**。ユーザーは仮名を1文字も打っていない。
  誤答時の部分表示も `K.toKakikudashi(problem.tokens, orderTrayIndices())`（kudashi.js:216）で、
  並びだけがユーザー由来。
- **採点は配列比較**。`grade()`（kudashi.js:153-201）は置き字の混入 → 白文トレイの残り →
  再読文字の枚数 → `got` と `want` の先頭一致長 `k`、の順に見るだけ。仮名は関与しない。
- **カードは `data-i` と `data-nth` を持つ**（kudashi.js:74-76）。再読文字の2枚目は
  `［＋］`ボタン（kudashi.js:98-109）で複製され `data-nth="2"` が付く。
  **入力を格納するキーの土台はすでにある**。

### 1.2 中核ロジック側の状態

`kanbun.js` には仮名を扱う関数が**揃っているが、UI から一度も呼ばれていない**。

| 関数 | 行 | 現状 |
|---|---|---|
| `tokenReading(t, nth)` | 113-121 | 3分岐（`reread` / `kana` / 通常）。カタカナ→ひらがな変換 `KATA2HIRA` を通す |
| `toKakikudashi(tokens, order)` | 123-132 | `seen` Map で同じ index の出現回数を数え `nth` を決める |
| `normalizeKana(s)` | 135-141 | カタカナ→ひらがな・記号除去・`ゐゑを`→`いえお`・`ぢづ`→`じず` |
| `kanaEquals(a, b)` | 145-148 | 上に加えてハ行転呼（`transposeHagyo`、**文字列先頭を除く**）を両辺にかけて比較 |
| `matchesKakikudashi(input, problem)` | 149-152 | `kakikudashi` と `acceptable[]` を照合。**リポジトリ全体でどこからも呼ばれていない**（`grep` 済み） |

さらに **`acceptable[]` は全58問で空**。つまり「自由入力を正規化して照合する」経路は
**一度も実データで動いたことがない**。設計書 §4.3 が最大の設計リスクと呼んだ流派差の吸収は、
API だけあって中身が無い状態にある。

### 1.3 この作業の目的

1. 書き下し練習を「並べる」だけから「**読みまで自分で作る**」に進め、
   東北大 第四問②・阪大の「すべて平仮名で」・早稲田 文/法の白文設問（`exam-kanbun-sources.md` §2-7-2）に
   実際に届く形にする。
2. そのとき **作業量で離脱させない**（設計書 §5「毎回フル組み立ては作業になり離脱要因になる」）。
3. **原則1（表記ではなく読み順で判定する）を仮名の層でも守る**。
   訓点で表記の一意性を要求しなかったのと同じ理由で、仮名でも表記の一意性を要求しない。

## 2. 6つの論点

### 論点1: プリセット候補をどこから作るか

#### 測定した事実

| 測定 | 値 |
|---|---|
| 異なり字数 | 226 |
| そのうち corpus 内で**読みが1種類しかない字** | **175（77%）** |
| 送り仮名の異なり | 100 種（**うち62種は corpus 全体で1回だけ**） |
| 送り仮名を持たないトークン | 118 / 376（置き字を除いた総数のおよそ 1/3） |
| 再読文字に使われている字 | **未・応・猶・且**（4字。再読文字は全部で9字） |

#### 案の比較

| 案 | 中身 | 利点 | 欠点 |
|---|---|---|---|
| **A. 他問題から集める** | 同じ字が他の問題で取る `yomi`/`okuri` を候補にする | 新規データゼロ。同期ずれが原理的に起きない。**多義字（与・如・為・之・見）では教材として最良**（「与」は corpus 内で「と／か／よリハ」の3読み） | **77% の字で候補が0件**。問題を足すたび候補が変わる（テストの固定が要る） |
| **B. 字ごとの読み表を別ファイル** | `yomi-table.json` を新設し、226字ぶんの頻出読みを人が書く | 候補の質が最も高い。「その字の頻出読み」という §6.3 の文言そのまま | 226字ぶんの新規著述。**texts.json と同期する不変条件が1本増える**（表に載っていない読みが texts.json に出たら破綻）。README が繰り返す「人の記憶に頼らない」道具立ての逆を行く |
| **C. 機械生成** | 正解の送り仮名から活用系列をたどって別の形を作る | 常に候補が出る。**送り仮名の学習内容そのもの**（＝どの活用形かを選ぶこと）に一致。決定的にできるのでテストで固定できる | 読み仮名（音読み／訓読みの選択）には使えない。もっともらしい偽の訓読みは作れない |

#### 結論（推奨）

**A ＋ C のハイブリッドを採る。B は採らない。ただし再読文字にだけ B を局所適用する。**

- **送り仮名 → C を主・A を従**。
  `kanbun.js` に**活用系列の定数 `OKURI_FAMILY`** を持つ（データではなくコード。日本語文法の閉じた知識で、
  texts.json と同期する必要がないため）。正解が属する系列から別の形を最大3つ取り、
  足りなければ (1) 同じ字の corpus 内他用例（A）、(2) corpus 全体の頻出送り仮名（ヲ・ニ・ハ・ノ・ズ）、
  (3) **「送り仮名なし」**（1/3 のトークンが該当するので必ず候補に入れる）で埋める。

  ```
  OKURI_FAMILY（初期案・テストで削る前提）
    ハ行四段    : ハ ヒ フ ヘ ホ
    打消        : ズ ザル ザレバ ザリ ヌ ネ
    形容詞      : シ キ ク カラ カリ ケレバ
    サ変        : ス スル スレバ セ シ
    ラ行        : ル ラ リ レ
    接続        : テ ニシテ シテ トモ ドモ バ レバ
    使役        : シム シメ シムル シメバ ヲシテ
    助詞        : ヲ ニ ハ ノ ト ヨリ
  ```

- **読み仮名 → A のみ**。候補が作れる字（51字）でだけ候補を出し、
  **作れない字では読み仮名を問わない**。これは論点3の段階分けと接続する
  （読み仮名を問うのは上位段 K3 だけで、そこでは自由入力が主になる）。

- **再読文字 → B（閉じた表）**。9字しかなく、1回目・2回目の読みは事実上固定なので、
  `kanbun.js` に `REREAD_PRESETS`（9字 × first/second）を持つ。
  corpus には4字しか出ないので A では足りず、C では作れない。
  **9字で閉じている＝保守コストが有限**なので、ここだけ表を持つのは合理的な例外。

**B を退ける理由をもう一段**: この repo の品質保証は「二重帳簿」（`validateProblem` が
訓点→読み順→書き下しを突き合わせる）と「機械検査」（`kuho-check.js` / `qa/check.js`）で成り立っている。
226字の読み表は**人が保守する第2の真実**になり、texts.json と食い違ったときに
どちらが正かを機械が決められない。A＋C は既存データからの**導出**なので、この矛盾が発生しない。

#### 候補生成の仕様（純粋関数として `kanbun.js` に置く）

```
okuriChoices(problems, pid, i, nth) -> { answer: string, choices: string[] }
```

- **決定的**（`Math.random` を使わない）。シードは `pid + ':' + i + ':' + nth` の簡易ハッシュ。
  理由: テストで固定できないと「答えが3番目に偏る」といった事故が検出できない。
- **重複除去は `normalizeKana` で行う**（`kuho.js:138,153` の `seen` Set と同じ手口）。
  「ハ」と「は」を別候補として出さない。
- **「偶然正解になる肢」を除外する**。候補 `c` でその位置を差し替えて文を組み、
  `matchesKakikudashi` が真になるなら捨てる。
  README:51 に記録された **L2 の誤答肢生成と同じ原則**（読み順シミュレーションで偶然正解になる肢を除外）を
  仮名の層に移す。ハ行転呼のせいで「ハ」と「ワ」が同値になるといった事故がここで自動的に消える。
- 候補数は **4〜5**（正解1＋ダミー3〜4）。除外の結果3つを割ったら「なし」と頻出送り仮名で補う。
- 入口で **`t.decoy`（任意フィールド）があればそれを最優先で使う**という3行を書いておく。
  データ側は当面空のままにするが、機械生成が明らかに悪い候補を出す箇所を
  1箇所だけ手で上書きできる逃げ道になる（chem の `acceptable` と同じ思想）。

### 論点2: 採点をどうするか

#### 決定的な証拠

`kanaEquals` のハ行転呼は `transposeHagyo = s => s.replace(/(?!^)[はひふへほ]/g, ...)` で、
**文字列の先頭を除外している**（kanbun.js:144）。したがって:

```
K.kanaEquals('ハ', 'わ')                          → false   ← カード単体
K.kanaEquals('思ひて', '思いて')                   → true    ← 文脈つき
K.kanaEquals('信にして疑はれ…', '信にして疑われ…') → true    ← 文全体
```

これは机上の話ではない。`ukemi-utagau`（「信而見疑、忠而被謗」）の
**「見」は `yomi:'' / okuri:'ハレ' / kana:true`** で、このカード単体の読みは **「はれ」**。
文の中では「疑**は**れ」となって非先頭なので現代仮名遣い「疑**わ**れ」と一致するが、
**カード単体で採点すると「われ」と入れた学習者が落ちる**。

これは決定事項 **U5「歴史的仮名遣いで持ち、現代仮名遣いも正解にする」に真っ向から反する**。

#### 原則1との整合

設計書 §2 の原則1は「返り点の打ち方は一意でないから、表記ではなく生成される読み順を比べる」。
仮名の層に置き換えると:

> **送り仮名の分担と仮名遣いは一意でないから、カードごとの文字列ではなく、
> 組み上がった文の読みを比べる。**

送り仮名がどのカードに乗るかは実際に一意でない。上の `ukemi-utagau` がまさにそれで、
「疑はれ」の「はれ」は**「疑」ではなく「見」のトークンに乗っている**。
学習者が「疑」に「ハレ」を書いても訓読としては正しい。
カード単位で採点することは、訓点で避けたはずの「表記の一意性を要求する」罠にそのまま落ちること。

#### 結論（推奨）

**合否は文全体で、指摘はカード単位で。**

```
gradeReadings(problem, order, inputs) -> { status, sentence, divergeAt, message }
  status: 'ok'      … matchesKakikudashi が problem.kakikudashi と一致
          'variant' … acceptable[] のどれかと一致（クリア扱い。登録の形を併記する）
          'wrong'   … どれとも一致しない
```

- `inputs` は **`{ '3:1': {yomi, okuri}, '0:2': {...} }`** の形（キー = `index:nth`）。
  **未入力のキーはデータの値をそのまま使う**。これで K2（送り仮名だけ問う）と
  K3（全部問う）を同じ関数で扱える。
- 実装は **`tokenReading` / `toKakikudashi` に一切手を入れない**。
  差し替えたトークンの複製を作って既存関数に渡すだけ ＝
  `grade(userMarks, problem)`（kanbun.js:162-166）が `userMarks` でトークンを複製しているのと同じ作法。
- `wrong` のときだけ、別関数で最初に食い違うカードを求める:

  ```
  firstDivergentCard(problem, order, inputs) -> { pos, i, nth } | null
    order を頭からたどり、kanaEquals(ユーザーの読み, データの読み) が偽になる最初の位置
  ```

  **この関数は合否に一切関与しない**（上の「はれ／われ」で偽陰性を出すため）。
  赤く塗る位置を決めるためだけに使う。既存 `grade()` の `divergeAt` と同じ見せ方に揃う。
- 判定は**2段**にする。第1段＝現在の並び判定（kudashi.js の `grade()`）、
  第2段＝読みの判定。**並びが違う間は読みを採点しない**（誤答の理由を1つに絞る＝原則2）。

`variant` を用意することで、**`acceptable[]` に初めて消費者ができる**。
現在は空なので当面 `variant` は出ないが、流派差の報告が来たときに
データを1行足すだけで吸収できる形になる（コードを直さない）。

### 論点3: どこまでを必須にするか

#### 測定した事実

| 測定 | 値 |
|---|---|
| 1問あたりのトークン数 | 中央 7 / 最大 12 |
| **1問あたり「送り仮名を持つカード」** | **平均 4.4 / 中央 5 / 最大 8** |
| 6枚以上ある問題 | 58問中 12問 |
| 送り仮名が無いトークン | 118（1/3） |
| 読み仮名が空のトークン | 31（ほぼ `kana:true` の助字） |

全カードに読み仮名と送り仮名を入れさせると、1問あたり 7 枚 × 2欄 = **14 回の入力**になる。
設計書 §5 が名指しで警戒した「作業」そのもの。

#### 結論（推奨）

**3段にする。既定は K2（送り仮名だけ・プリセット）。**

| 段 | 与えるもの | ユーザーの操作 | 対応する入試の形 |
|---|---|---|---|
| **K1**（現状・変更なし） | 読み仮名トグル | 並べ替えのみ。読みは自動生成 | 語順感覚の土台 |
| **K2**（新規・本命） | 読み仮名は**常時表示**（`showYomi` を強制ON） | 並べ替え＋**送り仮名をプリセットから選ぶ** | 九大・早稲田・明治文・法政文・學習院文（返り点＋送り仮名の記入） |
| **K3**（新規・上位） | 何も与えない | 並べ替え＋読み仮名・送り仮名を**自由入力**（候補は「候補を見る」の奥） | 東北大 第四問②・阪大「すべて平仮名で」 |

**なぜ送り仮名が先で、読み仮名が後か**（3つとも測定・調査の裏づけがある）:

1. **入試で問われるのは送り仮名**。`exam-kanbun-sources.md` §2-7-2 が挙げる L3 直撃校
   （九大・早稲田4学部・明治文・法政文・學習院文）はいずれも「返り点**と送り仮名**を付す」形。
2. **読み仮名は候補が作れない**。論点1のとおり 77% の字は corpus 内で読みが1種類しかなく、
   プリセットが成立しない。プリセットが成立しない段を「既定」にはできない。
3. **読み仮名は L1〜L3 でも表示されている既知情報**（game.js:225-236 がルビとして描いている）。
   当てさせても学習価値が薄い一方、送り仮名は**どこにも表示されていない未知の情報**。

**問うカードは上限5枚**にする。

```
askableOkuri(problem) -> number[]   // 送り仮名を問うカードの index（と nth）
  除外: 置き字（role:'placed'）
  対象: okuri が空でないカード、および再読文字の1枚目・2枚目
  枚数が5を超える問題では、先頭から5枚に絞る（読む順で先の5枚）
```

中央値が5なので**ほとんどの問題では実質「全部」**、8枚ある長い問題だけが3枚免除される。
「上限を設計で決める」ことに意味があり、問題を足していっても作業量が発散しない。

**段の切り替え**: ツールバーにセグメント（`K1 並べる｜K2 送り仮名｜K3 自力`）を置く。
既定値は **`PR.isClear(problem.id, 'K')` が真なら K2、偽なら K1**。
＝ 設計書 §5「新しい型の初回だけ上の段を出し、2回目以降は下の段に戻す」の逆向き適用で、
**一度クリアした問題は次に開いたとき自動的に一段上がる**。

**`progress.js` は変更しない**（論点3の重要な結論）。
`MODES = ['L1','L2','L3','K']` に `K2`/`K3` を足すと `stateOf()` の `'all'` 判定が
4個→6個になり、**既存ユーザーの「◎」が「○」に降格して見える**（progress.js:57-61）。
どの段でクリアしても `markClear(id, 'K')` を呼ぶだけにする。
段ごとの到達記録は当面持たない（「やらないこと」§6）。

### 論点4: 再読文字と置き字

#### 再読文字（corpus では 未・応・猶・且 の4字。全体では9字）

データは `reread: { first: {yomi, okuri}, second: {yomi, okuri, kana} }`。
`rongo-misei` の「未」は first `いま／ダ`、second `／ズ（kana:true）`。

**結論**:

- **カード2枚それぞれに独立した入力を持たせる**。カードは既に `data-nth` を持ち
  （kudashi.js:75, 96-109）、`tokenReading(t, nth)` が `nth` を受ける（kanbun.js:113-118）ので、
  **`inputs` のキーを `index:nth` にするだけでロジック側の変更はゼロ**。
- **1枚目と2枚目で候補の系列を分ける**。1枚目は副詞的な送り（ダ／ニ／ホ／ツ）、
  2枚目は助動詞（ズ／ベシ／ントス／シ）。`REREAD_PRESETS` を9字ぶん持つ（論点1の B の局所適用）。
- **2枚目は `kana:true`＝漢字を出さない**。入力面の見出しを
  「2回目（**ひらがなだけ**で読む）」と明示し、プレビュー行に「未 → **ず**」と出す。
  カードには既に `.nth2` クラスで別の背景色が付いている（kudashi.html:88）ので、そこに合わせる。
- **順序の縛りを可視化する**。2枚目のカードは `order` 上で必ず1枚目より後にある。
  入力面のヘッダに「1枚目／2枚目」と現在位置を出す。

#### 置き字（corpus では17トークン・14問）

`role:'placed'` ＝ 読まない。既に「読まない箱」へ捨てる操作がある。

**結論**:

- **置き字カードには入力欄を開かない**。タップ（＝入力ボタン）自体を出さない。
- **代わりに「働きの行き先」を教える**。置き字カードの入力ボタンの位置に **`?`** を置き、
  押すと入力面ではなく説明面が開く:

  > 「而」は**読みません**。ただしその働きは、前の「**学**」の送り仮名 **ビテ**（→ 学び**て**）に出ています。

  これは設計書 §3.1-2「置き字は order から除外するが、その働きは前の字の okuri に入る。
  **これを知らずに実装すると書き下し生成が必ず狂う**」を、実装者の注意事項から**学習者への教材に転じる**もの。
- 「前の読み字」を求めるには `kanbun.js` の `prevReadable(tokens, i)`（kanbun.js:26-29）が使えるが、
  **現在 export されていない**（return 文 kanbun.js:224-226 に無い）。
  **`prevReadable` / `nextReadable` を export に追加する**（純粋関数・既存の意味を変えない）。
- 置き字が「読む順」トレイに紛れ込んでいる状態は既存 `grade()` が先に弾く（kudashi.js:157-162）ので、
  読みの採点まで到達しない。順序はそのままでよい。

### 論点5: 既存の並べ替え UI との共存

#### 確認した事実（`sortable-lite.js`）

| 事実 | 行 |
|---|---|
| `pointerdown` で `if (e.target.closest("input, button, select, textarea, a")) return;` ＝ **カード内の入力・ボタンは掴まない** | 191 |
| `itemFrom()` は**リスト直下の子まで遡る**ので、カード内に何を入れても掴み対象はカードのまま | 36-41 |
| `touchmove` の `preventDefault` は **`drag.started` のときだけ** ＝ ドラッグしていない間のスクロールは阻害しない | 167-169 |
| タッチは `delay:180` の長押しで開始。**長押し前に動かしたらドラッグを諦めてスクロールに譲る** | 145-153, 209-217 |
| `kudashi.js` は `itemSelector:'.card'`・`delay:180`・`delayOnTouchOnly:true`・`touchStartThreshold:6` で3トレイを同一グループにしている | kudashi.js:57-68 |
| 既存の `［＋］`ボタンはこの仕組みで動いている（`<button class="dup">` ＋ `ev.stopPropagation()`） | kudashi.js:98-109 |

**したがって、カード内に `<button>` を置くこと自体は既に実証済みで、衝突しない。**

#### 残る本当のリスク

1. **カード全体をタップして開く設計にすると、ドラッグ終了時に `click` が誤発火しうる**。
   `sortable-lite.js` は `click` を抑止していない（`endDrag` は `pointerup` で終わるだけ、125-140行）。
   同じ位置に戻すドラッグでは `click` が飛ぶ。
2. 短押し（180ms 未満）ではドラッグが始まらないので、タップとドラッグは**時間で分離できてはいる**。
   ただし 1. の穴を塞ぐ手当てが要る。

#### 結論（推奨）

**カード全体タップではなく、カード上の専用ボタンで開く。**

- カードの `.yomi` スパン（現在ただの表示・kudashi.html:79-82）を
  **`<button class="reading">` に変える**。中身は「送り仮名を選ぶ」なら現在値または `＋送り`。
- `［＋］`（`.dup`）と同じく `ev.stopPropagation()` を呼ぶ。
- **`click` 誤発火の問題が原理的に起きない**（ボタンは `closest("button")` で pointerdown 段階から
  ドラッグ対象外なので、そもそも drag が始まらない）。
- カード本体のドラッグは**まったく変更しない**。既存の操作感が壊れない。
- 保険として `Sortable` の `onStart` でフラグを立て `onEnd` から 250ms 無視する
  ガードを入れてもよいが、上の方式では不要になる。**入れないことを推奨**（不要なコードを足さない）。

### 論点6: モバイルでの操作

#### 確認した事実

- `#boards` は `display:flex; flex-wrap:wrap` で **3列（白文／読む順／読まない箱）が横並び**
  （kudashi.html:49-53）。
- `@media (max-width: 600px)` で `.board { min-width: 6.8em; padding: 0.4em }`（kudashi.html:107-110）。
  **カード幅はおよそ 6em 弱**。ここに入力欄と4〜5個の候補ボタンを差し込むのは物理的に無理。
- `.tray` は `max-height: 26em; overflow-y: auto`（kudashi.html:56-60）＝ トレイ自体がスクロールする。
  カードの中を伸ばすとトレイ内スクロールが増え、並べ替えのオートスクロール（`autoScroll`、
  sortable-lite.js:71-76）と体感が悪くなる。

#### 案の比較

| 案 | 評価 |
|---|---|
| カード内にインライン展開 | **不可**。6em 幅に候補ボタンが入らない。トレイの高さが動いてドラッグ中の位置が狂う |
| ポップオーバー（カードの隣に浮かせる） | 3列レイアウトの隣列に重なる。狭い画面では画面外に出る。位置計算が要る |
| **ボトムシート** | **推奨** |
| モーダル（中央・全画面） | 対象カードが見えなくなる。「どのカードを編集中か」が失われる |

#### 結論（推奨）

**ボトムシート（`position: fixed; left:0; right:0; bottom:0`）を採る。**

理由:

1. **カード幅に依存しない**。3列レイアウトを1行も変更せずに済む。
2. **`document.body` 直下に置けば `sortable-lite` と完全に無関係**。
   `instanceFor()` はトレイ要素しか登録していない（sortable-lite.js:43-46）ので、
   シート内の要素はドラッグ判定にまったく掛からない。
3. **候補ボタンを 44px 以上で並べられる**。プリセット既定＝タップ主体という §6.3 の方針と噛み合う。
4. **開いている間、対象カードが画面に残る**。シートは画面下 40% 程度に抑え、
   開いたときに対象カードを `scrollIntoView` してハイライト（既存の `.good`/`.bad` とは別の
   `.editing` クラス）する。
5. **前後送りをシート内に置ける**。`◀ 3/5 ▶` で**シートを閉じずに次のカードへ移れる**。
   これが作業量の体感を決める（論点3の離脱対策の実装面）。1問5枚なら
   シートを1回開いて5回タップ＋4回送りで終わる。

**デスクトップも同じシートを使う**（実装を1本にする）。幅だけ `max-width: 34em; margin: 0 auto` で中央寄せ。
`@media` の分岐を増やさない。

閉じ方: シート外タップ／`×`／`Esc`。**閉じても入力は保持する**（`inputs` オブジェクトが真実で、
シートは編集ビューにすぎない）。

## 3. データモデルの変更

### 結論: **`texts.json` のスキーマ変更は不要。既存58問への影響はゼロ。**

理由:

- 正解はすべて既存フィールドにある（`yomi` / `okuri` / `kana` / `reread.first|second` / `role`）。
- 候補は corpus からの導出（A）と活用系列からの生成（C）で作るので、**新しいフィールドが要らない**。
- 再読文字の候補表は `kanbun.js` 内の定数（`REREAD_PRESETS`）＝ JSON ではない。

### 足すのは「コード側の定数」だけ

| 置き場所 | 名前 | 中身 | なぜ JSON でないか |
|---|---|---|---|
| `kanbun.js` | `OKURI_FAMILY` | 活用系列 8 系列（論点1） | 日本語文法の閉じた知識。作品データではない |
| `kanbun.js` | `REREAD_PRESETS` | 再読文字9字 × first/second | 9字で閉じている。texts.json と同期する必要がない |

### 任意フィールド（**今は入れない**が、受け口だけ作る）

| フィールド | 用途 | 方針 |
|---|---|---|
| `t.decoy: string[]` | 機械生成が悪い候補を出す1箇所を手で上書き | **候補生成器の入口で見る3行だけ書き、データ側は空のまま**。必要が生じてから足す |
| `p.acceptable: string[]` | 流派差の別解（**フィールドは既に存在し、58問すべて空**） | **K3 を出すまで空のままでよい**。K2（プリセット）は選択肢しか受け付けないので別解が発生しない。K3 の実装と同じコミットで埋め始める |

**`acceptable` が空のまま K3 を公開してはいけない**、というのがここでの重要な含意。
自由入力を許した瞬間に「正しいのに落ちる」が発生し、それを吸収する唯一の仕組みが空だからである。
K3 を後回しにする（論点3・実装計画）ことでこのリスクを先送りできる。

### 4.1 カード（変更点は1つだけ）

```
現在                          変更後（K2）
┌──────────────┐             ┌──────────────┐
│ ③            │             │ ③            │
```

- 未入力のカードは薄い破線の枠（`.needs-input`）。**残り枚数が一目で分かる**。

### 4.2 ボトムシート

```
┌───────────────────────────────────────┐
│  ◀   3 / 5 枚目   ▶                 × │   ← 前後送り。閉じずに次のカードへ

│                                       │
│        思                             │   ← 対象の字を大きく。読み仮名「おも」を上に添える
│        おも                            │
│                                       │

│  ┌────┐┌────┐┌────┐┌────┐┌──────┐  │
│  │ ハ ││ ヒ ││ フ ││ ヘ ││ なし │  │   ← プリセット（4〜5個・44px 以上）
│  └────┘└────┘└────┘└────┘└──────┘  │      「なし」は必ず入れる（1/3 が該当）
│                                       │
│  ▸ 自分で書く                          │   ← 折りたたみ。開くと <input> が出る
│                                       │

│  学びて思(   )ざれば則ち罔し             │   ← ライブ更新。未入力は (   )
└───────────────────────────────────────┘
```

- **下端の「いまの書き下し」がこの画面の主役**。設計書 §6.2 の
  「打った瞬間に書き下しがライブで更新される／変な文が出ること自体がフィードバックになる」を
  そのまま書き下し練習に持ち込む。候補を押すたびに1文字ずつ文が育つ。
- 「自分で書く」は**折りたたみの奥**（プリセット適用が既定、という §6.3 の指示どおり）。
  K3 ではここが既定で開いた状態になる。
- 入力は**仮名のみ**を受け付ける（漢字はデータのまま。カードの漢字を打ち直させない）。
  カタカナ／ひらがなどちらで入れてもよい（`normalizeKana` が吸収する）。

### 4.3 判定後の見せ方

- **`ok`**: 既存どおりカードを緑に。書き下しを大きく表示。
- **`variant`**: 緑にしたうえで「登録の形は『◯◯』です」と併記（§4.3 の `variant` の作法に揃える）。
- **`wrong` かつ並びが違う**: **現状のまま**（読みは採点しない）。理由を1つに絞る。
- **`wrong` かつ並びは合っている**: `firstDivergentCard` のカードを赤くし、
  シートをそのカードで自動的に開く。メッセージは
  「**3枚目「思」の送り仮名が違います**（いまの文: 学びて思**ふ**ざれば則ち罔し）」。
  ＝ 誤答時に「なぜ変な文になるか」を文で見せる（原則2）。
